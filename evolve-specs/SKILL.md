# Evolve Specs 技能

本技能用于为代码项目生成、演化和维护标准化的规范文档体系。

## 功能概述

1. **初始化 specs 目录结构** - 在指定目录创建标准的 specs 目录
2. **生成架构文档** - 分析项目代码，生成架构设计文档和架构规范文档
3. **创建特性文档** - 为项目特性生成设计文档和规范文档
4. **演化现有文档** - 当代码或架构变更时更新对应的 specs 文档
5. **审视优化文档** - 检查文档的逻辑性、完备性和合理性，进行系统性优化

## 目录结构

```
specs/
├── arch/
│   ├── design.md          # 架构设计文档
│   └── rule.md            # 架构规范文档
└── feat/
    ├── feat_001_{name}/   # 特性目录
    │   ├── design.md      # 特性设计文档
    │   └── rule.md        # 特性规则文档
    └── feat_002_{name}/   # 更多特性...
```

**特性目录命名规则**：`feat_{index}_{name}`
- `{index}` - 三位数字编号，从 001 开始递增
- `{name}` - 特性名称，使用下划线分隔单词

详细结构说明请参考 `references/specs_dir_example.md`。

## 模板文件

本技能使用以下模板文件生成文档：

| 文档类型 | 模板文件 |
|----------|----------|
| 架构设计文档 | `references/arch_design_template.md` |
| 架构规范文档 | `references/arch_rule_template.md` |
| 特性设计文档 | `references/feat_design_template.md` |
| 特性规范文档 | `references/feat_rule_template.md` |

生成文档前，**必须**先读取对应的模板文件。

## 工作流程

### 1. 初始化项目 specs

当用户要求为项目生成 specs 时：

1. 确认目标项目目录（默认为当前工作目录）
2. 检查是否已存在 specs 目录
3. 创建 specs 目录结构
4. 分析项目代码结构和技术栈
5. **读取** `references/arch_design_template.md` 模板
6. 生成架构设计文档 (specs/arch/design.md)
7. **读取** `references/arch_rule_template.md` 模板
8. 生成架构规范文档 (specs/arch/rule.md)

### 2. 创建特性文档

当用户要求创建特性文档时：

1. 确认特性名称和描述
2. 检查 specs/feat 目录，确定下一个可用的特性编号
3. 创建特性目录 `feat_{index}_{name}`
4. **读取** `references/feat_design_template.md` 模板
5. 生成特性设计文档 (design.md)
6. **读取** `references/feat_rule_template.md` 模板
7. 生成特性规范文档 (rule.md)

### 3. 演化现有文档

当项目代码变更需要更新 specs 时：

1. 分析变更内容
2. 更新相关的架构文档或特性文档
3. 保持文档与代码的一致性

### 4. 审视优化文档

当用户要求审视和优化 specs 时：

1. 读取完整的架构设计和规范文档
2. 检查以下方面：
   - **逻辑性**：文档内部逻辑是否一致，有无矛盾
   - **完备性**：是否覆盖所有必要的内容，有无遗漏
   - **合理性**：设计决策是否合理，有无更好的方案
   - **一致性**：设计文档和规范文档是否一致
3. 进行系统性优化（只优化不删减）

## 核心设计原则

### 1. 分层架构原则

| 层级 | 职责 |
|------|------|
| 应用层 | 用例编排、流程控制、状态管理 |
| 领域层 | 业务逻辑、策略实现、数据模型 |
| 基础设施层 | 数据持久化、外部服务集成 |
| 服务层 | 具体服务实现 |

**依赖规则**：
- 应用层可依赖领域层和服务层
- 领域层不可依赖应用层
- 服务层不可依赖应用层
- 基础设施层不可依赖应用层

### 2. 外部依赖复用原则

项目 **MUST** 明确标注外部依赖，**MUST NOT** 重复实现已有能力。

### 3. 接口扩展原则

**扩展接口应通过 Protocol 或 dataclass 定义**：
- 行为扩展：使用 Protocol 定义接口契约
- 配置扩展：使用 dataclass 定义数据结构
- 避免使用抽象基类，保持灵活性

### 4. 版本管理原则

- 配置变更应保存为新版本，**MUST NOT** 覆盖已有版本
- 使用版本号或时间戳标识不同版本

## 文档内容要点

### 架构设计文档 (arch/design.md)

核心章节：
- 设计思路（动机、目标、非目标）
- 设计原则（优先级、权衡）
- 架构图（使用 Mermaid）
- 技术选型及理由
- 模块组成和交互关系
- 类图和数据模型
- 状态图（如适用）
- 关键用例运行视图
- 代码目录组织
- 风险与决策

### 架构规范文档 (arch/rule.md)

核心章节：
- 总则（目的、范围、规范层级）
- 架构公约（分层、模块化、接口设计）
- 代码目录组织规范
- 代码实现规范（命名、函数、类、注释、错误处理）
- 安全规范
- 性能规范（如适用）
- 测试规范
- 版本控制规范
- 规范执行与豁免

### 特性设计文档 (feat/*/design.md)

核心章节：
- 设计动机和目标
- 架构/逻辑图
- 类图（如适用）
- 数据模型
- 状态图（如适用）
- 关键用例运行视图
- 实现思路和方案
- API 设计（如适用）

### 特性规范文档 (feat/*/rule.md)

核心章节：
- 特性边界公约
- 数据访问规范
- 业务逻辑规范
- 接口设计规范
- 代码实现规范
- 安全规范

## Mermaid 图表规范

优先使用 Mermaid 语法绘制图表：

| 图表类型 | 适用场景 | 语法 |
|----------|----------|------|
| 架构图 | 模块关系、系统组成 | `graph TB` / `graph LR` |
| 流程图 | 业务流程、算法流程 | `flowchart TD` / `flowchart LR` |
| 时序图 | 模块交互、调用流程 | `sequenceDiagram` |
| 类图 | 类结构、继承关系 | `classDiagram` |
| 状态图 | 状态流转、生命周期 | `stateDiagram-v2` |

## 注意事项

1. **不要重复造轮子** - 如果项目中已有架构文档或设计文档，应在此基础上完善而非重新生成
2. **保持一致性** - 特性文档应与架构文档保持一致，遵循架构规范
3. **增量更新** - 更新文档时只修改必要的部分，保持文档稳定性
4. **Mermaid 图表** - 优先使用 Mermaid 语法绘制图表，便于版本控制和渲染
5. **语言一致性** - 文档语言应与用户沟通语言保持一致
6. **外部依赖** - 明确标注项目依赖的外部模块和复用关系
7. **扩展机制** - 清晰定义扩展接口（Protocol、dataclass）而非抽象基类
8. **模板使用** - 生成文档前必须先读取对应的模板文件，确保格式一致
